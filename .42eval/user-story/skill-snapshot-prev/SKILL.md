# 用户故事（三个最小故事）

## 核心原则

**层级**：`real.md → cog.md → pr.spec.md → userstory.spec.md → sys.spec.md → Work`

**信息密度规则**：生成的故事只包含人类需要告诉 AI 的信息。每行通过测试："cog.md + real.md + pr.spec.md + AI 通用知识都不含这个信息吗？"

**上游引用检查**：写每节前，先确认上游文档是否已包含该信息。若已覆盖，仅用一行引用（如"见 real.md §C1"），不复制内容。

遵循 INVEST 原则。

## 适用场景

- 将 pr.spec.md 中的需求拆解为可执行的用户故事
- 为功能定义验收标准和故事地图
- 评估故事类型分布是否合理

## 不适用场景

- 需求尚未明确（先用 product-requirements 技能）
- 系统架构设计（由下游 sys.spec 承载）
- 迭代排期和人员分配（属项目管理范畴）

## 前置条件

1. 读取 `real.md`（项目根或 `.42cog/`）→ 提取硬约束
2. 读取 `cog.md` → 提取智能体类型、核心实体
3. 读取 `pr.spec.md` → 提取功能需求和 MAS 故事

缺失时先调用对应技能创建。

## 三个最小故事

| 类型 | 模式 | 编号前缀 | 应用场景 |
|------|------|----------|----------|
| 光明 | 从坏到好 | MS-L-XX | 目标达成、能力获得 |
| 黑暗 | 从好到坏 | MS-D-XX | 错误处理、异常恢复 |
| 灰色 | 循环往复 | MS-G-XX | 日常操作、效率优化 |

**黄金比例**：MVP 70/20/10 → 成长 50/30/20 → 成熟 40/20/40

**复杂度启发式**：每个 MS 对应一个用户可感知的状态转换。

## 故事层级

- **复杂故事（CS-XX）**：完整用户旅程，包含 3-8 个 MS，跨越多个迭代
- **最小故事（MS-[L/D/G]-XX）**：不可再分的用户价值单元，1-3 天完成

## 流程

### 1. 识别复杂故事

从 pr.spec.md 中提取用户旅程，形成 CS。不要使用通用分类（如"用户入门/核心功能"），从实际产品需求推导。

```markdown
## CS-XX: [故事名称]
**描述：** [完整用户旅程]
**用户类型：** [来自 cog.md 的智能体]
**核心价值：** [用户获得的主要价值]
**类型分布：** 光明 X / 黑暗 Y / 灰色 Z
**包含故事：** MS-L-XX, MS-D-XX, ...
**旅程：** [起点] → [关键节点] → [终点]
```

### 2. 编写最小故事

```markdown
### MS-L-XX：[标题]

**所属**：CS-XX | **类型**：光明 | **优先级**：P0/P1/P2

**用户故事**：
作为 [用户类型]，我想要 [做什么]，以便 [获得什么价值]

**故事评判**：
```

按类型选择对应评判字段：

**光明（从坏到好）**：
- 起点：[当前困境] → 转折：[系统提供的能力] → 终点：[达成目标]

**黑暗（从好到坏）**：
- 起点：[正常状态] → 转折：[出现的问题] → 终点：[识别并恢复]

**灰色（循环往复）**：
- 循环模式：[重复操作] → 优化点：[效率提升] → 习惯形成：[从费力到自动化]

```markdown
**用户可感知变化**：
- 操作前：[看到/感受到什么]
- 操作中：[执行什么动作]
- 操作后：[看到/感受到什么变化]

**验收标准**：
- [ ] [可测试标准1]
- [ ] [可测试标准2]

**约束**：见 real.md §[对应约束编号]
**依赖**：需要 [前置] / 使能 [后续]
```

### 3. 创建故事地图

按迭代组织，用树形结构展示：

```
迭代1（MVP）:
├── CS-XX: [名称]
│   ├── MS-L-XX: [标题]（光明）
│   ├── MS-D-XX: [标题]（黑暗）
│   └── ...
└── CS-YY: [名称]
    └── ...

迭代2: ...
```

## 输出结构

生成 `userstory.spec.md`：

```markdown
# 用户故事规格书

## 复杂故事概览
| CS | 名称 | MS数 | 优先级 | 类型分布 |

## CS-XX: [名称]
### MS-L-XX: [标题]
[完整最小故事]

## 故事地图
[迭代分解]

## 故事类型分布
| 迭代 | 光明 | 黑暗 | 灰色 |
```

## 反模式

| 错误 | 正确 |
|------|------|
| 复制 real.md 约束内容 | 用引用："见 real.md §C1" |
| 创建通用 CS 分类（用户入门/核心功能等） | 从 pr.spec.md 实际需求推导 |
| 在故事中写实现细节 | 聚焦用户可感知变化 |
| 跳过故事评判 | 每个 MS 必须有类型对应的评判 |
| 填充 AI 已知的通用知识 | 只写项目特有信息 |
| 使用通用示例（注册/登录） | 用占位符标签，从实际产品填充 |

## 质量检查

- [ ] 每个 MS 对应一个用户可感知的状态转换
- [ ] 故事类型分布符合产品阶段的黄金比例
- [ ] 约束来自 real.md 引用，非复制
- [ ] 验收标准可测试，无模糊描述
- [ ] 无 AI 已知的通用信息填充
